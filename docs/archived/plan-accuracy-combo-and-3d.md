# 実装計画：将棋としての正確化・駒の立体感・戦法×囲いの一体化

将棋の囲い図鑑（`shogi/index.html`）を「改善・修正・リッチ化・高度化・正確化」する計画。
調査は `js/ui/board-view.js`・`js/modes/*.js`・`js/data/*.js` の精読と、将棋の定説との照合に基づく。

要件の一覧：

1. **将棋としての正確性**：データ・説明文の誤りを直す（§1）
2. **駒アニメーション**：歩が左右に滑る等の違和感を直し、駒は移動方向（歩なら上下）に動かす（§2）
3. **戦法と囲いの一体化**：「矢倉囲い＋棒銀」のような組み合わせを盤に合成表示する（§3）
4. **分類マップの地図を削除**：木の図（デンドログラム）だけにする（§4）
5. **駒をフォトリアルに**：Three.js で立体の駒にする（§5）
6. **解説パネルの見せ方**：特徴の目安をペンタグラムにして上部へ／タグは `#` 表記／タブを廃止して一続きに（§6）

## 1. 将棋としての正確性：レビュー結果と修正項目

データ整合（駒数・座標重複・出典参照・経路の合法性）は `tools/validate-castles.js` がすべて通っており、配置も大半は定形と一致（舟囲い系・矢倉・穴熊・美濃系・カニ・兜・雁木・ボナンザ等）。見つかった修正点は次のとおり。

### 1-1. 高：`tactics.js` 九間飛車（`kyukenbisha`）の文脈が矛盾

- `context: '対居飛車（相手の左美濃・雁木の端を狙う）'` は誤り。**対居飛車で相手玉のある端は1筋側**であり、9筋は相手玉から最も遠い端。引用先（将棋神ラー記事）も「角道を開けてこない振り飛車に対して有力」と述べており、主な文脈は**相振り飛車**（後手美濃が8二側＝9筋に近い）。
- `desc` の「相手玉の近くの端を攻める」と `pros` の「相手玉から遠い側を攻められる」が**直接矛盾**。
- 修正：`context` を相振り（角道を開けない振り飛車相手）に直し、`pros`/`desc` の「近い/遠い」を整合させる。局面の囲いは開示済みの美濃のままか、記事推奨の左美濃に寄せるかは Q1 で判断。

### 1-2. 中：関連囲いリストと盤面の齟齬（2件）

- `bougin`（棒銀）：盤面 `玉78 金68 金58 銀57 銀26` は `funa68kin`（6八金型）の形そのものだが `castles: ['funa','yagura']` に `funa68kin` がない → 追加。
- `mukaibisha`（向かい飛車）：盤面は片美濃型＋攻め参加の左金（金7八）。`castles` に `katamino` がない → 追加。

### 1-3. 中〜低：系統の形状定義と分類の齟齬

- `kani`（カニ囲い）・`kabuto`（兜矢倉）は `family:'gangi'` だが、taxonomy の雁木型の定義「逆V字：銀が前へ出る」に合わない（カニの銀6八は横並び、兜の7七銀・7八金は矢倉骨格）。`refFamily` 注記とも矛盾気味 → 系統定義の文面を「銀が前または横に並ぶ壁型」系に広げるか、別系統への移し替えを検討（Q2）。

### 1-4. 低

- `bonanza` の `refFamily`：「ポナンザ囲いと誤記されることもある」→ ポナンザは誤記ではなく Bonanza 後継ソフト由来の別称。「Ponanza 由来の表記もある」に改める。
- `hayakurigin` の `lead.files:[4,3]`：3筋型は定説が曖昧。意図を確認（Q3）。
- `sankenbisha` の `desc`：盤面は 角77 のノーマル形だが説明は石田流（角8八で角道を開ける）に言及。「組み換えの可能性」を明確化して誤読を防ぐ。
- `ratings` の `side`：穴熊 side:5 は「横からの飛車攻めへの耐性」として妥当だが端攻めとの混同を避けるため、評価軸の定義をヘルプに明記。
- `gincan` cons の sq `['39','49','59']`：39 は空きマスなので強調としては弱い。実際の弱点マスに見直し。

### 1-5. 実施方法

- 各修正は `js/data/` の値と文面だけの変更。`validate-castles.js` を通し、関連囲いの追加は `castles` 配列の存在チェックで担保される。
- フェーズ0として最初に行い、1コミットにまとめる。

## 2. 駒アニメーション：歩の横滑りを直し、移動方向に動かす

### 2-1. 原因（`js/ui/board-view.js`）

- `render()` は駒を毎回 `innerHTML` で作り直し（`:28-36`）、`_flip()`（`:84-101`）が「同じ駒文字同士を距離順に貪欲ペアリング → 直線 translate」で滑らせる。
- 歩は9枚すべて `data-p="歩"` で区別不能。純粋な距離マッチなので、別筋の近い歩にペアを取られて**横滑り・逆方向（後退）に滑る**ことがある。
- 副次的問題：
  - マッチしない旧駒は innerHTML 置換で**フェードなしに瞬間消滅**（新駒のフェードインしかない）。
  - `.pc.gote` の `goteIn` アニメが innerHTML 再生成のたびに再生される（利き表示の切替など、駒が動かない再描画でも）。

### 2-2. 設計

**(a) マッチングに駒種コストを入れる**（汎用・全画面で有効）

`_flip` の距離 `d` を「駒の動きの不自然さ」を足したコストに置き換える：

```text
cost = dist + (歩・香で Δ筋≠0 ? 大) + (歩・香で後退 ? 中) + (桂で Δ段<0 ? 中) + …
```

- 歩・香：同じ筋（Δf=0）を強く優先 → **歩は必ず筋の中を上下に滑る**。同筋に相手がいなければフェードインに逃がす（コスト上限を設定）。
- 銀・飛・角：進行方向の射線上を優先。玉・金は全方向可到達なので現状維持。
- コスト上限を超えるペアは作らず「消滅＋出現」にする（不自然な長距離滑りを防ぐ）。

**(b) 戦法の主役駒は route を実際にたどる**（§3との相性も良い）

- `tactic.route`（例 `['39','38','47','56']`）は `validate.js` が「末尾=lead.square」を保証済み。`board.render()` に `trace` 情報を渡し、主役駒だけは route の各マスを経由するキーフレームで折れ曲がって動かす。
- 経路矢印の出現タイミング（`tactics.css` の 0.55s 遅延）は FLIP の 560ms に合わせてあるので、キーフレーム所要時間に合わせて調整。

**(c) 消える駒にフェードアウト** — 未ペア旧駒を一時的に残して `opacity 1→0` で消す（(a) との対称性）。

**(d) goteIn の再生抑制** — `.pc.gote` の入場アニメは「新たに出現した後手駒」のみに限定（`data-sq` をキーに出現済み駒を覚えるか、(a) のマッチングで対応付いた駒は animation クラスを付けない）。

### 2-3. 触るファイル

- `js/ui/board-view.js`：`_flip` をコスト方式へ、`trace` オプション、フェードアウト、gote 抑制
- `js/modes/tactic-mode.js`：route を render に渡す
- `css/board.css`：`goteIn` の適用条件、必要なら退場クラス
- `js/core/attack-map.js` の STEPS/SLIDES は「進める方向」の逆算に流用可能

## 3. 戦法と囲いの一体化：「矢倉囲い＋棒銀」を盤に合成表示

### 3-1. 方針

戦法画面の「相性のよい囲い」（`tactic-detail-view.js` の `.tc-castle` 一覧）で囲いを選ぶと、**共有の盤に「戦法の局面＋囲いの形」を合成して表示**する。もう一度押すと解除。従来の「囲いの画面へ移る」操作は別ボタン（例：囲い名の横に「→」リンク）として残す。

### 3-2. 局面の合成（新規 `js/core/combo.js`、約50行）

両者とも先手の全20駒の完全セット（`validate.js` の `fullSet`）なので**和集合ではなく置換合成**：

1. ベース = 戦法の局面（lead 駒は `role:'lead'` を保持、他は support）
2. 囲いの `core`→`support` の順に各駒 `(種, マス)` を適用：
   - 目標マスに同種の駒がいれば `role:'core'` に格上げ
   - なければ盤上の**同種の別駒**（lead・適用済みを除く、最も近いもの）を取り除き、目標マスへ置く
   - 目標マスに居た別種の駒は持ち駒へ（`Position.hand` 機構は既存）
3. lead 駒のマスは動かさない（主役を守る）

枚数整合は構造上自動的に保たれ、あぶれた駒が持ち駒として `stage-f .hand`（`stage-view.js:22` 既存）に見える。

### 3-3. 見せ方

- 表示モード `core`（囲いのみ強調）が「囲いの駒＋戦法の主役」を強調する効果を自然に出せる。
- `overlay.skeleton`（囲いの骨格線）と `overlay.route`（戦法の経路）はどちらも既存機構で、合成時は両方を重ねる。
- 見出しを「棒銀 × 矢倉囲い」の併記に。解説欄に選択中囲いの名前・一文説明を折りたたみ表示し、両者の出典を併記。

### 3-4. 触るファイル

- 新規 `js/core/combo.js`（合成ロジック）＋ `manifest.js` 登録
- `js/modes/tactic-mode.js`：合成局面の render、`skeleton` の併用
- `js/ui/tactic-detail-view.js`：`.tc-castle` に「盤に重ねる」操作を追加
- `js/ui/tactic-stage-view.js`：併記見出し
- `js/app.js`：store に `tacticCastleId` キー追加（未選択=合成しない既定）
- `js/core/validate.js`：合成結果を任意で検証する経路（Q4）

## 5. 駒をフォトリアルに：Three.js による立体駒

### 5-1. 現状と境界

- 駒は `.pc > i > span` の DOM＋clip-path 五角形＋漢字。`.pc` を触るのは **`board-view.js` だけ**で、駒レイヤを差し替える境界は非常にきれい。
- 盤は完全に表示専用（`.sq`/`#board` に操作ハンドラなし）→ **canvas は `pointer-events:none` でよく、レイキャスト不要**。
- 設計制約：**file:// でも動く**（ES module / import map を使わない古典スクリプト構成）。

### 5-2. 構成（盤全面 1 キャンバス方式を推奨）

- `#board` 内に `position:absolute; inset:0; pointer-events:none` の透明 canvas を1枚、`.squares`（マス線・ヒート・ハイライト）と `.overlay`（骨格・矢印 SVG）の間の z-index に挟む。
- `OrthographicCamera` でマス座標 `x=(9-f+.5)*W/9, y=(r-.5)*H/9` に駒メッシュを配置（盤は 9:9.6 の非正方なので注意）。
- 駒：五角形 `Shape` の `ExtrudeGeometry`（台形断面で側面に傾斜）＋駒面は `CanvasTexture` アトラス（駒種×owner×role の漢字を Shippori Mincho で焼く。`document.fonts.ready` 後に生成）。朱字・後手の青はテクスチャ側で対応。
- 照明：環境光＋斜め上からの指向性光＋柔らかい影（影用の薄いメッシュ or `shadowMap`）。
- `.pc.off/.hidden` → `material.opacity`、後手は `rotation.z=π`、§2 のアニメはメッシュ tween に移植。
- テーマ色は `getComputedStyle` で CSS 変数を読み、`data-theme` 変更時にアトラス・マテリアルを再生成（MutationObserver か ThemeToggle から通知）。

### 5-3. file:// 制約への対応

- Three.js は ESM 移行済みだが、**UMD ビルド（`three.min.js`）が残る最終系（例: r147〜r152 台）を `js/vendor/` にベンダリング**して manifest で読む。CDN 参照は file:// 直開きで不安定なため避ける。バージョンは公開から十分経過した安定版をピン。

### 5-4. 移行ステップ

1. `board-view.js` の `.pc` 生成を `pieceLayer` 抽象に分離（DOM 実装をラップ）
2. Three.js 版 `pieceLayer` を追加し `#board` に canvas を重ねる（`ResizeObserver`・DPR 対応、cluster 画面では描画停止）
3. §2 のコスト式マッチング・route 軌跡をメッシュ tween に移植
4. DOM 駒レイヤは削除（or `?flat` パラメータで残しフォールバック — Q5）

- リスク：テクスチャ生成コスト・フォント読込タイミング・プリファレンス（`prefers-reduced-motion`）の三重ガード踏襲。
- スクリーンショット検査（ui-check.js）が見た目回帰の検出経路になる。

## 6. 解説パネルの見せ方（囲いモード右パネル）

### 6-1. 特徴の目安 → ペンタグラム

- `detail-view.js` の `_ratings`（5軸×5段階）を **SVG レーダーチャート（正五角形）** に置き換え、**パネル最上部**（タグより上）に配置。
- 軸順は現行どおり（堅さ・玉の広さ・上部の強さ・横の強さ・組みやすさ）。罫線グリッド5段・値の多角形は墨線＋薄い塗り、頂点の軸ラベルは小さく周囲に。
- 数字の各行表示は残さず、軸名＋グラフで完結させる（hover で値を見せてもよい）。

### 6-2. タグ → `#` ハッシュタグ表記

- 現状 `.tag` は罫線枠のチップでボタンに見える → 枠を外し `#舟囲い型` `#基本形（7九銀・6八銀）` `#対振り飛車` `#急戦` のように `#` 前置きのテキストリンク風にする（クリック不可・装飾のみ。クリック可能にするなら系統絞り込みへの導線にできる — Q6）。

### 6-3. タブ廃止 → 一続きの表示

- `#detailTabs`（概要／長所・短所／攻め筋／出典）を撤去し、`detail-body` に **概要→特徴ペンタグラム→囲いの駒→長所→短所→攻め筋→出典** の順で全セクションを縦に並べる（`.sec h3` の見出し＋罫線スタイルは既存）。
- `DetailView` の `pane`/`showTab` 機構を削除、`render` は単一 HTML を出力。`setAttack` の選択状態更新は残す。
- 戦法の解説（`tactic-detail-view.js` の 概要／組み方／相性のよい囲い／出典）も同様に一続きにする（同じ見せ方で統一）。
- `index.html` から `#detailTabs` の seg を除去、`castle-mode.js` の `detailTabs` 参照を除去。
