# 統合計画：制約条件で描く一枚の画面

`plan-matchup.md`（M0〜M5）の続き。囲い図鑑・戦法周期表・対局図の3画面を、**制約条件のリスト**で描く1画面にまとめる。あわせて次の3点も行う。

- 左右のドックを広げ、選択UIをタイル化する
- 囲い・戦法の未収録分を追加する
- 本文中に出典番号 `[n]` を入れる

> 前提：別セッションの未コミット変更（compat の pairing ok 上書き、rail の属性更新化、hover 連動、hash の部分URL判定、後手スライドの回転保持など）を、関心ごとに分けてコミットしてから着手する。以下の行番号はその時点のもので、ずれうる。

## 1. 制約モデル

### 1-1. データ構造

```js
// 並び順＝優先度（末尾ほど新しく、優先される）
constraints: [
  { who:'opp', kind:'strategy', id:'furibisha' },
  { who:'opp', kind:'tactic',   id:'shikenbisha' },
  { who:'me',  kind:'castle',   id:'funa' },
]
selected: 'me.castle'          // `${who}.${kind}`。右ドックで説明する対象
```

- `(who, kind)` の組ごとに制約は最大1つ。同じ組を選び直すと置き換わり、リストの末尾へ移る。
- `kind` は `strategy | tactic | castle` の3種類。戦型（相居飛車・角換わりなど）は制約にしない。選択状態から**導出したラベル**として表示する（§1-4）。
- 指定のない層は、戦略の既定値で補う。補った値は**暗黙の制約**と呼び、制約バーに点線のチップで薄く表示する。削除ボタンはつけない。クリックすると説明を表示し、左ドックで選び直すと通常の制約に昇格する。
  - いまの `pick` 配列は、このリストの並び順に吸収される。値と優先度を二重に管理する必要がなくなる。
- 相手の制約が1つも無いときは、**相手の駒を描かない**。これで旧画面と同じ表示が自然に得られる。
  - 自分の囲いだけを指定 → 旧・囲い図鑑と同じ表示
  - 自分の戦法だけを指定 → 旧・戦法周期表と同じ表示
  - 両者を指定 → 旧・対局図と同じ表示

### 1-2. 正規化（既定値を補う規則を1か所にまとめる）

いま既定値で補う処理は `compat.js` / `matchup.js` / `matchup-mode.js` / `matchup-rail-view.js` の4か所に重複している（調査結果より）。これを `js/core/constraints.js` の1関数にまとめる。統合作業の前提になる。

```js
Kakoi.constraints.sides(list) -> {
  me:  { strategy, tacticId, castleId, implied:{strategy?,tactic?,castle?}, rank:{strategy,tactic,castle} },
  opp: { ... } | null,                      // 相手の制約が無ければ null
}
```

- `rank` はリスト内の位置。存在しない層は -1 とする。いまの `resolve` が使っている「pick の古い順」の情報になる。
- `compose` / `compat` / `matchup` / 各ビューは、すべてこの出力を受け取る。`oppStrategy` の扱いが非対称だった問題（compat には渡し、mode には渡していなかった）もここで解消する。

### 1-3. 追加・変更・削除と自動解決

```js
Kakoi.constraints.apply(list, op) -> { list, changed:[{who,kind,from,to,why,dropped?}] }
  // op: {type:'set', who, kind, id} | {type:'remove', who, kind}
```

1. `set` のときは、同じ `(who,kind)` の制約を取り除き、新しい制約を末尾に足す。`remove` のときは取り除くだけにする。
2. 同じ側（`who`）のほかの層を、優先度の低い順に `compat.judge` で確かめる。ng なら、既存の `searchAlternative` と同じ規則（a: 相性表の◎、b: 相手との fitness、c: 同じ系統、d: 動く駒の数が最小）で差し替える。
3. **解が無いときは、その古い制約を削除する**（`dropped:true`）。戦略の既定値どうしが必ず ok であることは unit-test で保証済み。したがって「ng のまま残る」状態（調査で見つかった `unresolved`）は原理的に起きなくなる。
4. **連鎖は同じ側の中だけで起こす**。相手の制約は、自分の選択によって変わらない。両軍の駒がぶつかる場合は、これまでどおり盤上の「接触＝開戦」の印で示す。
5. 歩同士の接触で1段下げる側（`merge` の `late`）は、いまは `'opp'` 固定になっている。これを「リストの中で後ろにある側」に変える。

### 1-4. 導出ラベル（戦型）

制約バーの右端に、削除できない灰色のラベルとして表示する。例：`#対抗形` `#角換わり`。

| ラベル | 条件 |
|---|---|
| 相居飛車 / 対抗形 / 相振り飛車 | 両者の戦略から決める（既存の `matchup.threat().kind`） |
| 角換わり・相掛かり・横歩取り・矢倉・雁木 | 両者とも居飛車であり、かつ両者の戦法の `senkei` タグに共通するもの。矢倉と雁木は、自分の囲いの系統でも判定する |
| 角換わり（補助） | 持ち駒に角がある戦法（腰掛け銀など）を含む |

## 2. 状態・URL・永続化

```js
// 新しい state（board ビュー）
{ view:'board' | 'cluster',
  constraints:[...], selected:'me.castle',
  dock:{ split:0.5, top:{who:'opp', tab:'tactic'}, bottom:{who:'me', tab:'castle'} },
  mode, heat, skeleton, heatScope, showThreat, attackId, clusterFamily }
```

- `castleId` / `tacticId` / `matchup` / `familyFilter` / `lastBySide` は廃止する。読み込み時に古い値を制約へ変換する。
  - `view:'castle' + castleId` → `[{me,castle}]`
  - `view:'tactic' + tacticId` → `[{me,tactic}]`
  - `matchup` → `me` と `opp` の3層を、`pick` の順に並べたもの
- URL ハッシュは `#k=os:furibisha,ot:shikenbisha,mc:funa&sel=mc` の形にする。並び順が優先度になる。
  - 旧形式（`v=` / `c=` / `t=` / `ms=` など）は `hash-link.js` で上記の規則に従って変換し、新形式で書き直す。
  - `dock`・`mode`・`heat` は URL に載せない（表示の好みなので、これまでどおり）。
- `dock` は localStorage に保存する。ドラッグ中は CSS 変数だけを書き換え、ドラッグを終えたときに `store.set` する。

## 3. 選択肢の表示（左ドックのバッジ）

### 3-1. 2つの軸

| 軸 | 値 | 見た目 |
|---|---|---|
| **整合**：選ぶと、自分の側のほかの制約が変わるか | `free`（変わらない） / `cascade`（変わる） | `cascade` は破線の枠にし、右肩に変更の要約をつける。例：`→居飛車`、`→四間飛車・美濃` |
| **対敵**：相手との相性 | `good` / `neutral` / `bad`（相手の制約が無いときは非表示） | `good` は朱の左帯に◎と理由の小チップ（`#縦に強い`）。`bad` は△と理由を `title` に出す。`neutral` は印なし |

- いまの `level:'ng'` は「選べない」ではなく `cascade` として表示する（要件4・5）。
- 色だけに頼らない。破線・◎・△といった記号と、要約の文字を必ず併記する。
- 対敵の判定方法：
  - 囲い：既存の `fitness` の上位帯を `good` にし、下位帯（最高点から1.0以上低い）を `bad` にする。
  - 戦法：`against`（相手の戦略）に加え、新しく `againstTactic`（相手の戦法 id）を使う。例：超速▲3七銀は、対ゴキゲン中飛車で `best`。
  - これで、調査で指摘された「戦法の `against` が rail の◎に反映されていない」問題も解消する。

### 3-2. 計算コスト

`cascade` の要約を出すには、選択肢ごとに `apply` を試しに実行する必要がある。

- 1回の更新で対象になるのは、左ドックの上下に表示されている2面分だけ。最大で（戦法約30＋囲い約35＋戦略2）×2面。
- `judge` はメモ化済み。`apply` の試行結果は `JSON(list)+候補` をキーにして LRU に入れる。
- 目標は1更新あたり16ms以内。超える場合は、見えている範囲だけを先に計算し、残りは `requestIdleCallback` で埋める。unit-test に処理時間の上限テストを加える。

### 3-3. ホバーで予告する

選択肢にホバーまたはフォーカスすると、次の3つを予告する。

- 制約バーで、変更される予定のチップを点滅させる
- 盤で、動く予定の駒のマスを `board.hover(squares,'focus')` で示す
- ×理由に関係するマスを `bad` で示す

実際に選んだときは、既存のアニメーションで駒を動かす。トーストには「元に戻す」をつける（リスト全体を1つ前に戻す）。

## 4. レイアウトと選択UI

### 4-1. 列幅

```css
.app { grid-template-columns: var(--col-l, minmax(320px, 1.45fr)) minmax(0, 1.75fr) var(--col-r, minmax(340px, 1.55fr)); }
.stage { grid-template-columns: minmax(0, 1fr); }   /* 既存のはみ出し（戦法画面で幅1280以下）を先に直す */
```

| 幅 | 現在（左/中/右） | 変更後の目安 |
|---|---|---|
| 1440 | 330 / 750 / 360 | 約 440 / 525 / 475 |
| 1280 | 330 / 590 / 360 | 約 380 / 455 / 410 |
| 1024 | 330 / 334 / 360 | 左右の下限（320/340）が効き、中央が狭すぎる → 1100 以下は §4-6 の折りたたみに切り替える |

- 盤は、1440 のとき約 650px から約 450px になる（面積は約半分）。周期表のセルは最小 10px の文字で、1筋あたり約 50px。「居飛車（2筋）」のような長い名前は、タイルでは**短縮名**（`short`）を使う。
- 980px 以下では、これまでどおり1列にする。左ドックは上下分割をやめ、タブで切り替える。

### 4-2. 左ドックの上下分割

```
┌ 左ドック ───────────────────────────┐
│ [相手|自分]  [戦略・戦法|囲い]  ▾   │ ← 上の面の対象切替
│   （タイル一覧・スクロール）          │
├──────── ═ ドラッグ ═ ────────┤ ← role=separator, aria-valuenow, ↑↓キー対応, ダブルクリックで50%に戻す
│ [相手|自分]  [戦略・戦法|囲い]  ▾   │ ← 下の面の対象切替
│   （タイル一覧・スクロール）          │
└─────────────────────────────┘
```

- 既定は、上が相手の戦法、下が自分の囲い。盤の向き（相手が上）とそろえる。
- 上下で同じ対象を選んでもかまわない。両方とも同じ store を見て更新されるので、表示は食い違わない。
- 戦略（居飛車／振り飛車）は各面の先頭に置く小さな Segmented にする。戦法タブと囲いタブのどちらでも表示する。戦略の選択にも §3 のバッジをつける。
- スプリッタは pointer events で実装する。最小の高さは 120px。比率は `dock.split` に保存する。

### 4-3. 戦法タイル

- **グリッド**：列は筋で、自分の面では 9→1、相手の面では盤の絶対座標に合わせて 1→9 にする（相手の四間飛車は盤の4筋に来るため）。行は、主役の駒の行（§6-2）。
- **1マスに1タイル**：タイルは「主役の駒の最終マス」単位で作る。同じマスに来る戦法は**派生**として束ねる（`variantOf`）。タイルを選ぶと、親の戦法が制約になる。派生は、タイルの下に展開されるチップか、右ドックで切り替える。
- **アイコン**：`tacticGlyph(tactic)` で自動生成する。主役の `route` を、5×5 程度に切り出した格子の上に折れ線で描き、終点に駒の字を置く。`family-glyph.js` と同じ流儀（currentColor、stroke 1.6）にする。
  - 手で描くと約40個になり、データとずれるおそれがある。経路から生成すれば正確さが保てる。
  - 角換わり系（持ち駒に角）は、アイコンの角に小さな◇をつける。
- タイルの中身は、アイコン、短縮名、筋の番号、バッジ（§3）。まれな戦法は、これまでの `data-rare` の表示を引き継ぐ。

### 4-4. 囲いタイル

- **クラスタ表示**：系統（`CASTLE_FAMILIES`。新系統を含めて9系統、§6-1）ごとに、見出しを置いて折りたためるブロックにする。見出しには系統のグリフ・名前・件数をつける。
  - 戦略と合わない系統（振り飛車のときの居飛車の囲いなど）は、ブロックごと `cascade` の見た目にする。隠さずに残す（要件4）。
- **サムネイル**：`miniBoardSVG` に `crop:'king-golds-silvers'` を追加する。
  - `role==='core'` の駒のうち、玉・金・銀の外接矩形に、上下左右1マスの余白をつけて切り出す。
  - 範囲に入った香・桂・歩は `.off`（薄く）で描く。穴熊の香桂は外接矩形のすぐ外にあるので、余白の1マスに入って見える。
  - 縦横比は正方形に寄せ、足りない方向は余白で埋める。囲いによる拡大率の差は、サムネイル間の比較を保つため、**最大の外接矩形に合わせた共通の倍率**を使う（Q3）。
  - 相手の面では、盤の向き（180度回転した位置）で描く。駒の字は正立のままにする。
- **大きさ**：いまのカード（92×116〜160）の約75%にする。左ドックが広がるので、1行に4〜5列入る。キー移動の `COLS=3` 固定は、CSS と二重管理になっている。実際の列数を `getComputedStyle` から求める方法に改める。

### 4-5. 盤上の筋ボタン（周期表）

- `selected` が `*.tactic` のときだけ表示する。暗黙の戦法を選択しているときも表示する。
- クリックすると `apply({type:'set', who: selected.who, kind:'tactic', id})` を実行する。対象は**選択中の側**の戦法。
- 相手の側のときは、列を `10−f` に反転して、盤の絶対的な筋にそろえる。見出しにも「相手の戦法」と明示する。
- 表示される行は、その側の戦略の行だけにする（居飛車なら居飛車の行）。もう一方の戦略の行は、ボタン列の下に折りたたみ、`cascade` の見た目で出す。
- 「順に再生」は周期表の右端に置き、選択中の側の戦法を順に送る。

### 4-6. 狭い幅

- 1100px 以下では、右ドックを開閉できるドロワーにする（制約チップをクリックすると開く）。
- 980px 以下では、これまでの1列表示（見る→選ぶ→読む）にする。

## 5. 右ドック（説明）

`selected` の種類ごとに、既存の詳細ビューを部品化して組み立てる。`DetailView` / `TacticDetailView` / `MatchupDetailView` は、**セクション部品**の集まりに分解する。

| 選択 | 内容（上から順） |
|---|---|
| `*.strategy` | 居飛車・振り飛車の説明（新規データ `STRATEGIES[].desc`）、その側の戦法と囲いの要約、相手がいれば戦型ラベルと「どちらからの攻めが主になるか」（§1-2 の距離の説明） |
| `*.tactic` | 戦法の詳細（これまでどおり）、派生の切替、相性のよい囲い（自分の囲いに対する ◎/○/連鎖）、相手との相性（`against` / `againstTactic` とその理由） |
| `*.castle` | 囲いの詳細（ペンタグラム・#タグ・長所短所・攻め筋）。相手がいれば、ペンタグラムに戦型の重みを重ね、fitness と効いている軸を表示する |
| 共通の末尾 | 両軍の接触・連鎖の履歴（直近の `changed`）、出典（§7） |

- 攻め筋（`attacks[].gote`）は、相手の制約が無いときだけ駒を表示する。相手がいるときは、狙われるマスと矢印だけを表示する（後手の駒が2組重なるのを避ける）。
- 説明の中にある `data-sq` のホバー連動は、これまでどおり。

## 7. 本文中の出典番号

- **データ**：本文の文字列に `[[ref]]` または `[[ref1|ref2]]` を書く。対象は `desc`、`pros/cons[].t`、`attacks[].t`、`pairings[].why`、`note`。既存の形（文字列）を変えずに済む。
  - 例：`'美濃囲いは横からの攻めに強い[[wj-mino]]。'`
- **表示**：`Kakoi.html.rich(text, citer)` を新しく作る。`esc` した後に、トークンを `<sup class="cite"><a href="#src-3">[3]</a></sup>` に置き換える。
  - 番号は、**右ドック1枚の中での出現順**に振る。末尾の出典リストも同じ番号で並べ直す。
  - 本文で引用されなかった出典は、リストの後ろに番号つきで続ける。
  - `[n]` にホバーすると、リストの該当項目を強調する。
- **出典リストの共通化**：いま3つのファイルに同じマークアップがコピーされているので、`sourcesBlock(items, citer)` にまとめる。
- **`title` 属性など**：プレーンテキストを入れる場所では、トークンを取り除く関数 `plain(text)` を通す（`matchup-rail-view` の `el.title` など）。
- **validate**：
  - ref が `SOURCES` に存在すること（エラー）
  - ref がその項目の `sources[].ref` に宣言されていること（エラー）
  - 宣言しているのに本文で一度も引用していない出典（**警告**。移行中に段階的に減らす）
- **移行の量**：対象は約216文字列。このうち desc 30件と pros/cons 120件を優先する。どの出典がどの文を裏づけるかの判断は、出典ページとの照合が必要なので、データごとに Sonnet のサブエージェントへ並列に割り振り、人が差分を確認する。
