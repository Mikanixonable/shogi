# 対局図計画：戦略・戦法・囲いを独立に選び、相手の駒組みと突き合わせる

## 0. ゴール

- 自分と相手のそれぞれについて **戦略 → 戦法 → 囲い** の3層を、どの順番でも選べるようにする（囲いを先に選んでから戦法、でもよい）
- 選択肢には、いまの選択との関係を3段階で表示する
  - **◎ 好相性**：盤上で両立し、定跡でも推奨される。相手の戦型に対しても強い
  - **○ 両立**：盤上で両立する
  - **× 両立しない**：駒がぶつかる、または将棋の原則に反する
- ×の選択肢を選んだら、**最後に選んだものを優先**し、ぶつかった側の層を両立する候補に自動で差し替える。駒はアニメーションで移動する
- 相手（後手）の駒組みも盤に表示し、同じ3層で選べるようにする。相手の戦型によって、自分の囲いのうち効く強みが変わる
  - 例：相居飛車なら縦（上部）に強い囲い、対抗形なら横に強い囲いを強調する

既存の「囲い図鑑」「戦法周期表」はそのまま残す。新しい第4の画面 **対局図** を足し、組み合わせの機能はそこに集約する。

## 1. 将棋としての前提（実装の根拠）

### 1-1. 戦略・戦法・囲いの関係

| 層 | 決めるもの | 本アプリのデータ |
|---|---|---|
| 戦略 | 飛車を2筋に置いたまま戦う（居飛車）か、振る（振り飛車）か。玉を囲う翼もここで決まる | 囲いの `side`、戦法の系統の `side` |
| 戦法 | 主役の駒（飛・銀）の位置と経路 | `TACTICS[].lead / route` |
| 囲い | 玉と金銀の形 | `CASTLES[].core` |

**玉飛接近すべからず**という格言のとおり、玉は飛車と反対の翼に囲うのが原則。居飛車なら左（7〜9筋）、振り飛車なら右（1〜3筋）に囲う。例外は右玉と、中飛車のように飛車が中央にある場合。

### 1-2. 戦型と攻めの方向

**相手の飛車の筋と自分の玉の筋の距離**で、主にどちらの方向から攻められるかが決まる。座標はすべて先手から見た絶対座標。後手の駒は (f, r) → (10−f, 10−r) で回転して置く。

| 戦型 | 例（自分の玉 / 相手の飛車） | 距離 | 主な攻めの方向 | 重視する強み |
|---|---|---|---|---|
| 相居飛車 | 矢倉の玉8八 / 相手の△8二飛 | 0 | **縦**：飛車先からの上部攻め、玉頭 | 上部（`top`）・堅さ |
| 対抗形・自分が居飛車 | 穴熊の玉9九 / 相手の△4二飛（四間） | 4〜5 | **横**：竜が入ったあとの横利き、端 | 横（`side`）・堅さ |
| 対抗形・自分が振り飛車 | 美濃の玉2八 / 相手の△8二飛 | 6 | **横**＋端、居飛車が持久戦なら**上部**（位取り・銀冠を目指す攻め） | 横・上部（相手の方針で変える） |
| 相振り飛車 | 美濃の玉2八 / 相手の△3二飛（三間） | 1 | **縦**：相手の飛車が玉の真上の筋に来る | 上部・堅さ（金無双・矢倉が主力になる理由） |

「美濃は横に強く縦に弱い」「矢倉は上部に厚い」「相振りは上部の厚さが大事」という定説は、すべてこの距離で説明できる。そこで戦型を名前のラベルだけで扱うのではなく、**距離から計算する**。こうすると、データに無い組み合わせ（九間飛車対中飛車など）でも理屈の通った強調ができる。

### 1-3. 盤上で両立しない理由の分類

全216組（12戦法×18囲い）をプロトタイプで判定し、次の5種類に整理した。結果は §8。

| コード | 内容 | 例 |
|---|---|---|
| `SQUARE` | 囲いの駒と戦法の必須の駒が同じマスに来る | 向かい飛車の飛8八と金矢倉の玉8八 |
| `KING_ROOK` | 玉と飛車の筋の差が1以下（玉飛接近） | 袖飛車の飛3八と美濃の玉2八 |
| `SAME_WING` | 玉と飛車が同じ翼にいる（中飛車・右玉は例外） | 右四間の飛4八と美濃の玉2八 |
| `COUNT` | 必要な駒の枚数が足りない | 3枚目の銀がいる組み合わせ。ただし §3-2 の「貸し出し」で救済する |
| `PAWN` | 合成すると二歩になる、歩・香を横に動かさないと作れない | — |

もう一つ、`TEMPO` という分類を置く。これは盤上では両立するが手数が矛盾するもので、例は急戦の棒銀と居飛車穴熊。×にはせず、○に「⚠ 組むのに手数がかかり、急戦の仕掛けに間に合いにくい」と注記する。

## 2. データ拡張

### 2-1. 戦法：`essential`・`pace`・`against`

```js
{ id:'bougin', ...,
  essential: '銀26 歩25 飛28',          // 戦法が手放せない駒。合成でもここは動かさない
  pace: 'rapid',                         // 'rapid'（急戦）| 'slow'（持久戦）| 'both'
  against: { furibisha: 'good', ibisha: 'ok' },   // 相手の戦略への適性（3段階の判定に使う）
}
```

| 戦法 | essential（案） | pace | against（案。要出典） |
|---|---|---|---|
| 九間飛車 | 飛98 角77 | rapid | furibisha: good（相振りで有効） |
| 向かい飛車 | 飛88 角77 | both | ibisha: good |
| 三間飛車 | 飛78 角77 歩76 | both | ibisha: good |
| 四間飛車 | 飛68 角77 歩66 | both | ibisha: good |
| 中飛車 | 飛58 歩56 | both | ibisha: good |
| 腰掛け銀 | 銀56 歩57 歩46 飛28 | both | ibisha: good |
| 早繰り銀 | 銀46 歩35 飛28 | rapid | ibisha: good |
| 棒銀 | 銀26 歩25 飛28 | rapid | furibisha: good, ibisha: good |
| 矢倉中飛車 | 飛59 | rapid | ibisha: ok |
| 右四間飛車 | 飛48 歩46 銀56 | rapid | furibisha: good（対四間）, ibisha: ok |
| 袖飛車 | 飛38 | rapid | ibisha: ok, furibisha: ok |
| 居飛車（2筋） | 飛28 | both | ibisha: ok, furibisha: ok |

`against` には、いまの自由文 `context`（「対居飛車」「相振り飛車」など）を構造化して入れる。`context` は説明文として残す。

### 2-2. 囲い：`support` を分ける。`flex` を足す

いまの `support` には「比較のために揃えた駒」（例：居飛車の囲いすべてに入っている銀26）が混ざっている。そのため戦法と合成すると、右四間の銀5六が2六へ引き戻されるなどの崩れが起きる（§8-C）。これを次の2つに分ける。

- `shell`：囲いの一部として意味がある歩・香・桂。矢倉の歩67・歩76、銀冠の歩26、穴熊の香98 など
- `filler`：比較用の補完。合成のときは使わない

`flex` は、戦法に貸し出してよい core の駒と、その行き先。

```js
{ id:'tsunogin', core:'玉69 銀67 銀47 金78 金58',
  flex: [{ sq:'47', to:['46','56','36'] }],   // 右銀は早繰り銀や腰掛け銀へ出てよい（現代雁木の実戦形）
}
```

`flex` が無いと、雁木＋腰掛け銀のような実戦の定番が `COUNT` で×になってしまう（§8-B）。

### 2-3. 戦略テンプレート：`STRATEGIES`

```js
Kakoi.STRATEGIES = {
  ibisha:    { label:'居飛車',   kingWing:'left',  defaultTactic:'ibisha-base', defaultCastle:{ vsIbisha:'yagura', vsFuribisha:'funa' } },
  furibisha: { label:'振り飛車', kingWing:'right', defaultTactic:'shikenbisha', defaultCastle:'mino' },
};
```

戦法も囲いも未選択のときは、これで「全駒の局面」を補う。いまの `SETUPS` は、この戦略テンプレートの `filler` として吸収する。

### 2-4. 相性表 `PAIRINGS`（◎の根拠）

戦法の `castles: [...]` を `{ castle, level, why, sources }` の形に置き換える。

```js
pairings: [
  { castle:'funa',   level:'best', why:'対振り飛車の急戦の定番', sources:[{ref:'joutatsu-bougin'}] },
  { castle:'yagura', level:'best', why:'相居飛車の矢倉棒銀',     sources:[...] },
]
```

- ◎は必ず出典つきにする。いまの `sources` の文化を引き継ぐ
- ○と×は、データから自動で判定する。人手で書くのは◎と、自動判定を覆すときの `level:'ng'`（理由つき）だけにする

### 2-5. いま直すべきデータ（プロトタイプで検出）

| 対象 | 問題 | 対応案 |
|---|---|---|
| `mukaibisha.castles` の `yagura` | 金矢倉の玉8八と向かい飛車の飛8八が重なる。矢倉の銀7七と角7七も重なる | 削除する。意図が「相振りの矢倉」なら、右側の矢倉（玉28 銀37 金38 金47。金矢倉を左右反転した形）を新しい囲いとして足してから結びつける |
| `nakabisha.castles` の `mino` | 本美濃の金5八と中飛車の飛5八が重なる | `katamino` だけにする。本美濃は「飛車が5五・5六へ浮いたあとの形」として注記つきの○にする |
| `koshikakegin.castles` | 角換わり腰掛け銀の主流である片矢倉（ボナンザ）型が抜けている | `bonanza` を◎で足す（要出典） |
| `sodebisha.castles` が空 | 導線が無い | 対振り（加藤流）の舟囲いを候補にする（要出典） |

## 3. コアロジック（`js/core/`、DOM に依存しない）

### 3-1. `compose.js`：層ごとに合成する

いまの `combinePosition`（戦法の局面に囲いを貪欲に置換する）を、ロックつきの層合成に置き換える。

```
compose({ strategy, tactic?, castle?, priority }) -> { position, conflicts[], moved }
  1. 土台：tactic があれば tactic.pieces、なければ STRATEGIES[strategy] のテンプレート
  2. ロック：tactic.essential（主役以外の必須の駒も保護する）
  3. castle.core を置く → ロックに加える
     （priority が castle のときは、手順2と3の順番を入れ替える。最後に選んだ層が勝つ）
  4. castle.shell を置く。ロック済みのマスは飛ばす
  5. 検証：二歩・行き所のない駒・駒の枚数。違反があれば conflicts に入れる
```

移し替える駒（donor）は、**その駒の動きで実際に行けるもの**に限る。

- 歩・香は同じ筋の後ろからしか持ってこない。横移動や後退は禁止。`piece-match.moveCost` が null かどうかで判定し、アニメーションの規則と共有する
- いまの実装は距離だけで donor を選ぶので、別の筋の歩を持ってきて二歩になる（§8-C の6件）
- ロックした駒は donor にしない。§8-C の主役ずれ33件の原因はここにある
- donor が無ければ持ち駒から補う。持ち駒にも無ければ `conflicts` に `COUNT` を積む

### 3-2. `compat.js`：両立判定

```
judge(sideState, layer, candidateId) -> { level:'best'|'ok'|'ng', reasons:[{code, squares?, text}], moved }
```

- 「いまの他の層」と候補を `compose` してみて、`conflicts` と §1-3 の規則（`KING_ROOK` / `SAME_WING` / `TEMPO`）から判定する
- `flex` で貸し出せる駒は `COUNT` と `SQUARE` から除く。貸し出した結果の囲いは「崩し形」として理由に書く
- `best` の条件は、`ok` であり、かつ次のどちらかを満たすこと
  - `PAIRINGS` に◎がある
  - 囲いの対戦相性スコア（§3-3）が、両立する候補の上位帯に入る。上位帯はスコア上位2件、または最高点から0.5以内
- 戦略と層の判定：戦略と `side` が食い違う戦法・囲いは `ng`（`SIDE`）にする
  - ただし飛車が5筋の戦法（中飛車・矢倉中飛車）は、`side` を戦略に合わせて読み替える
  - 例：矢倉中飛車＋美濃は×にせず、「振り飛車の中飛車として扱う」と注記する
- 計算量は、1回の選択につき候補は最大で 18（囲い）＋12（戦法）＋2（戦略）通り。毎回 `compose` を呼んでも十分に軽い。結果は選択状態をキーにメモ化する

### 3-3. `matchup.js`：対戦相性と強調

```
threat(me, opp) -> { kind:'aiibisha'|'taikou-i'|'taikou-f'|'aifuri', axis weights, threatFiles:[f] }
fitness(castle, threat) -> number   // Σ w_axis × ratings[axis]
```

- 戦型（`kind`）は §1-2 の距離で決める。距離 ≤ 2 なら縦が主、≥ 4 なら横が主、その間は両方を混ぜる。ラベルは表示用
- 重みの初期値は次のとおり。`ratings` の既存の5軸を使い、新しい評価は足さない

| kind | top | side | hard | wide | quick |
|---|---|---|---|---|---|
| 相居飛車 | .35 | .10 | .25 | .15 | .15 |
| 対抗形・自分が居飛車 | .10 | .35 | .30 | .10 | .15 |
| 対抗形・自分が振り飛車 | .20 | .30 | .25 | .10 | .15 |
| 相振り飛車 | .40 | .15 | .20 | .15 | .10 |

- 相手の戦法の `pace` で補正する
  - 相手が急戦なら `quick` と `side` を +.1 する。間に合う囲いが大事になる
  - 相手が持久戦なら `hard` と `top` を +.1 する。対抗形の振り飛車側では、高美濃・銀冠への発展が評価されるようになる
- 端攻めは5軸に含まれないので、囲いの `attacks` に `id:'hashi'` があり、かつ相手の戦法の主役の筋が端（1・9筋）または香・桂の経路が玉の筋に向くときだけ減点する
- 戦法の適性 `against[opp.strategy]` も同じ3段階で、相手の戦略を選んだときの戦法リストの強調に使う
  - 例：相手が四間飛車なら、右四間飛車・棒銀が◎になる

## 4. 状態と自動解決

### 4-1. state

```js
matchup: {
  me:  { strategy:'ibisha',    tacticId:'bougin',      castleId:'funa', pick:['strategy','castle','tactic'] },
  opp: { strategy:'furibisha', tacticId:'shikenbisha', castleId:'mino', pick:[...] },
  show: { opp:true, threat:true },
}
```

- `pick` は選んだ順の履歴で、最後の要素が最も優先される。いまの Store は `!==` で比較するので、更新のたびに新しいオブジェクトを作る
- `persistKeys` に加え、計画書 A-1 の URL ハッシュにも載せる。例：`#view=matchup&me=ibisha.bougin.funa&opp=furibisha.shikenbisha.mino`

### 4-2. ×を選んだときの自動解決

```
select(side, layer, id):
  1. side[layer] = id、pick の末尾に layer を移す
  2. 残りの層を、優先度の低いもの（pick の古い順）から調べる。いまの値が ng なら次の順で差し替える
     a. 新しい選択と PAIRINGS で◎のもの
     b. 対戦相性 fitness が最も高い ok
     c. 元の値と同じ系統（family）のもの
     d. compose の moved（動く駒の数）が最小のもの
  3. 戦略を変えたときは、戦法と囲いが ng ならテンプレートの既定値に戻す
  4. 変更があった層をトーストで知らせ、元に戻すボタンをつける
     例：「美濃囲いに合わせて、棒銀 → 四間飛車に変えました［元に戻す］」
```

- 決定的にする：同点なら `TACTICS` / `CASTLES` の並び順で決める。毎回同じ結果になることを単体テストで固定する
- 3層すべてが互いに ng になって解が無い、ということは起きない。戦略テンプレートの既定値どうしは必ず ok にし、それを validate で保証する

## 5. 相手の駒

- **データは先手用のものを回転して使う**：(f, r) → (10−f, 10−r)、`owner:'gote'`。後手専用のデータは作らない（計画書 C-5 の「L」を回避できる）
- **両軍がぶつかるとき**：駒組みの完成図どうしなので、同じマスに先手と後手の駒が来ることがある（例：自分の早繰り銀の歩3五と、相手の三間飛車の歩を回転した位置）
  - 後から選んだ側の歩を1段下げて置く
  - そのマスに「接触＝開戦」の印を出す
  - 歩以外の駒がぶつかるときは、ng（`CONTACT`）として扱う
- **アニメーション**：`pieceMatch.pair` の条件 `owner==='sente'` を「`owner` が一致すること」に広げる。3D と DOM のレイヤでは、後手の駒の `skip` と入場演出（回転・沈み込み）を「新しく現れた駒だけ」に限定する
- **利き・ヒートマップ**：`attack-map` は先手だけを数えている。相手の駒の利きは、**threat** の層として別の色で重ねる
- **脅威の表示**：`threatFiles`（相手の飛車の筋と、主役の経路の終点の筋）に縦の帯を薄く引き、相手の主役の駒の `route` を `tone:'bad'` で描く。これで「縦から来る」「横から回る」が盤上で見える

## 6. UI（対局図の画面）

```
┌ 相手（後手） ─────────────────────────────┐
│ 戦略 [居飛車|振り飛車]  戦法 ▾  囲い ▾     │  ← 折りたたみ可、既定は表示
├───────────────────────────────────────────┤
│                  盤（両軍）                │  脅威の帯・経路・接触の印
├───────────────────────────────────────────┤
│ 自分（先手）                               │
│ 戦略 [居飛車|振り飛車]                     │
│ 戦法  ◎棒銀 ○早繰り銀 ×四間飛車 …        │  ← 周期表の小さい版にバッジ
│ 囲い  ◎舟囲い ◎居飛車穴熊 ○矢倉 ×美濃 …  │  ← rail のカードにバッジ
└───────────────────────────────────────────┘
右パネル：戦型（相居飛車／対抗形…）・重視する強み・選択中の組み合わせの理由と出典
```

- **バッジの見た目**
  - ◎：朱の枠とバッジ
  - ○：標準
  - ×：薄く表示して斜線をかける。クリックはできる
  - いまの rail と周期表の `data-rare` と同じ要領で `data-compat="best|ok|ng"` をつける。カードの innerHTML は作り直さず、属性だけを更新する（`aria-current` と同じ経路）
- **理由の表示**
  - ホバーやフォーカスで、×の理由（例：「8八で玉と飛車が重なる」）を出し、該当するマスを `board.hover(squares,'bad')` で光らせる
  - 理由を色だけで伝えない。a11y（D-3）のため、記号とテキストを必ず添える
- **強調**
  - 対戦相性の◎には、理由のチップをつける（例：`#縦に強い 上部5`）
  - 右パネルのペンタグラムに、戦型の重みを薄い多角形として重ね、「どの軸が効くか」を見せる
- **既存画面との導線**

**A. 将棋の定説と合っている点**

- 戦略が食い違う組み合わせ（振り飛車の戦法×居飛車の囲い）は、60組のうち57組が×になった
- 居飛車同士は84組のうち71組が○になった
- ラベルを使わず駒の位置だけで判定して、この結果になった

**B. 規則を補う必要がある点**

- **雁木・ツノ銀雁木×銀の戦法が `COUNT` で×になる**
  - 実戦では、雁木の右銀が5六・4六へ出る形（雁木＋腰掛け銀）が定番である
  - §2-2 の `flex` で○（崩し形）に直す
- **矢倉中飛車×振り飛車の囲いが○になる**
  - 盤上では成り立つが、実質は振り飛車の中飛車である
  - §3-2 の戦略の整合で、戦法を「中飛車」として読み替える
- **中飛車×居飛車穴熊・矢倉が○になる**
  - 戦略の整合で×（`SIDE`）にする

**C. 合成ロジックの欠陥（両立と判定された組でも起きる）**

- 二歩が6件。矢倉中飛車×振り飛車の囲いで、別の筋の歩を donor にしたのが原因
- 主役ずれが33件
  - 例：右四間の銀5六・歩4六が、囲いの `support` にある銀26・歩47 を満たすために動かされる
  - 腰掛け銀の歩46、早繰り銀の歩35 も同じ理由で動く
  - 推奨されている組み合わせの右四間×舟囲い・穴熊でも起きている
- 対策は §3-1 の3点：essential のロック、`support` を `shell` と `filler` に分けること、駒の動きで行けるかどうかで donor を選ぶこと

再現用のスクリプトは scratchpad にある（`compat.js`）。M2 で `tools/unit-test.js` に取り込み、マトリクスをスナップショットにする。
